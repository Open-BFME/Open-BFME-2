### LINK-690: a bridged vtable retires by supplying the positive slot its class view lacks

Status: Open as a general entry; one table retired (2026-11-18). Updated: 2026-11-18; inspected revision `6d81f083db`; census index `582c2ca9fb` (census `96085b8989`).

`reverse/vtable_bridge_queue.tsv` carries, per bridged table, the retail slot list under `evidence.source_slot_mismatches`. Each entry names the slot index, the retail target RVA and the source copy's own relocation. A table whose only mismatches are `missing-source-slot` retires by declaring the slot's function in the class, because `vtable_bridge.slot_matches` only requires the copy's positive slot to relocate (DIR32, no addend) to a name `reverse/functions.csv` binds at exactly the retail target.

Two shapes, and only the first is a seat edit:

1. **The slot's body is already rowed, under this class or another owner.** Declare the virtual in the class at the matching index. If the body is rowed under a different mangled name, the emitted body must be byte-identical and relocation-free against it, and its own row must be admitted as an ICF fold (`tools/add_match.py ... --icf-owner <rowed name>`; the tool requires the owner row at the same RVA and size and byte-verifies the new row). `--notes` must not contain a comma.
2. **The slot is absent because the class view or a shared base disagrees with retail.** Two examples found on 2026-11-18, neither edited:
   - `??_7Watchdog@@6B@` (0x007E6FD8, 4 slots): the source copy's slot 1 is `ThreadClass::Execute`, so every later slot shifts; retail's slot 1 is `Watchdog::start` (0x002256C0). Fixing it means the `ThreadClass` view used here must not expose `Execute` as a virtual, which touches every ThreadClass consumer.
   - `??_7LargeGroupAudio@@6BSubsystemInterface@@@` (0x007E40A0, ≥5 slots): retail slot 4 is `?rva0020DB09@LargeGroupAudio@@UAE_NH@Z`; a derived-only virtual cannot land in a secondary base table, so `SubsystemInterface` itself needs the fifth virtual that `LargeGroupAudio` overrides. Shared-header work, not a unit edit.

Completed (2026-11-18, commit `1c025f8bab`): `??_7Rva005E1260Body@@6B@` at 0x00877990 wanted two slots — the deleting destructor (already matched through the `??_E` weak default of `??_G`) and 0x005E1222, the 36-byte body that invokes the member callback at +0xC on the object at +0x8. `Rva005E1260Body` declared only the destructor, so its copy was one slot. The class now types the payload words the constructor already copies as the target object and member-function pointer and declares `virtual Rva005E1222Value invoke()`. The emitted body is byte-identical and relocation-free against the rowed `?invoke@Rva005E1222@@QAE?AURva005E1222Value@@XZ` (36 B, `Code/GameEngine/Source/Common/Rva005E1222.cpp`), admitted as an ICF fold; the copy now relocates slot 1 to a name the ledger binds only at 0x005E1222. Verified locally: 6/6 rows exact in `Rva005E1260.cpp` (the four earlier rows unchanged) and `link_check` LINKS 143 -> 179 bytes. The queue is tool-owned and was not edited; confirmation is the next published real link, which must show neither `bridged` nor `refused` for this table.

Useful check before editing: build the one unit, then read the copy's slots straight from `build/match/<object>.obj` (symbol `??_7<Class>@@6B@`, section relocations) and compare the relocation names against the entry's slot list. After the change the slot must appear at the same index with the expected name; a shifted index is shape 2.
