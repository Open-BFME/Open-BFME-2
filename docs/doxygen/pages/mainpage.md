# Open-BFME-2 developer guide {#page_mainpage}

Open-BFME-2 rebuilds the engine of *The Lord of the Rings: The Battle for
Middle-earth II*, version 1.06, as C++. The engine binary is `game.dat`, and
every function written here must compile with Visual C++ 7.1 back to exactly
the bytes of the same function in the retail file. The retail binary is the
ground truth: the names and types in the source are reconstructions backed by
evidence, and some are still placeholders.

This guide is for developers who want to understand that code: what each part
of the engine does, how the parts fit together and how to read the source. It
is also written for modders and for people planning a remaster or a port, so
pages say, where the evidence allows, what is driven by game data, what is
fixed in code, and where a platform library could be replaced. The
repository's other documents (`README.md`, `AGENTS.md` and `docs/*.md`)
describe the matching work itself.

- **Modding:** start with \ref page_modding and the
  \ref page_mainpage_modding "modding notes" below.
- **Remastering or porting:** start with the
  \ref page_mainpage_remastering "remastering notes" below.

Every written guide and subsystem page has its own modding and remastering
notes, and class and function entries add them where there is something
specific to say.

## What is being rebuilt {#page_mainpage_target}

- **The target.** `baselines/bfme2/workshop-vanilla-1.06/` holds the retail
  `game.dat` and a manifest describing it: a 32-bit x86 Windows image built
  with the Visual C++ 7.1 linker. The `lotrbfme2.exe` launcher is a stub and is
  not a target.
- **The second binary.** The same directory holds `worldbuilder.exe`, the map
  editor. It is an unoptimised internal build of the engine source, with
  assertions, so its code reads much closer to the C++. Its PE header is dated
  January 2006, while `game.dat`'s PDB timestamp is September 2006 (its PE
  date is scrubbed), so a WorldBuilder body may predate 1.06 changes and
  serves only as a lead for names and structure; \ref page_reading_code says
  how far those leads can be trusted.
- **The ancestors.** BFME 2 runs on the SAGE engine, which descends from
  Command and Conquer Generals: Zero Hour. The `reference/open-bfme-1`
  submodule carries the Zero Hour source
  (`inputs/reference/CnC_Generals_Zero_Hour/GeneralsMD/`) and Open-BFME-1's
  reconstruction of BFME 1 (`game/`). Many BFME 2 functions are ported from one
  of them. This guide labels a fact taken from Zero Hour as "Zero Hour: ..."
  unless BFME 2 evidence confirms it.

## Where the code lives {#page_mainpage_layout}

The tree follows Zero Hour's split into `GameEngine`, `GameEngineDevice` and
`Libraries`. Paths are under `Code/`.

| Directory | What it holds | Pages |
|---|---|---|
| `GameEngine/Source/Main/` | `WinMain`, `GameMain`, `CreateGameEngine` and the Windows engine class `Win32GameEngine` (its constructor, update and subsystem factories) | \ref page_startup, \ref sub_engine_core |
| `GameEngine/Source/Common/` | the engine object, INI loading, the RTS model (players, teams, templates), file system, save and load; also the largest staging area of unattributed files | \ref sub_common_services, \ref sub_ini, \ref sub_rts_model, \ref sub_save_load_crc |
| `GameEngine/Source/GameLogic/` | the deterministic simulation: objects and modules, AI, pathfinding, map scripts, the map, the Living World campaign | \ref sub_objects_modules, \ref sub_ai_pathfinding, \ref sub_scripting, \ref sub_gamelogic_map, \ref sub_living_world |
| `GameEngine/Source/GameClient/` | per-machine presentation: drawables, FX, input, the message stream, GUI | \ref sub_gameclient, \ref sub_gui_apt |
| `GameEngine/Source/GameNetwork/` | lockstep networking, LAN and online code | \ref sub_network |
| `GameEngineDevice/Source/` | the platform layer: `W3DDevice`, `Win32Device`, `MilesAudioDevice` | \ref sub_w3d_rendering, \ref sub_audio |
| `Libraries/Source/` | EA and third-party libraries linked into `game.dat`: WWVegas (WWLib, WWMath, WW3D2), Apt, Lua, compression, DirtySock, video codecs and others | \ref sub_wwlib_thirdparty, \ref sub_memory |
| `gen_asm/`, `gen_small/`, `masm_dumps/` | generated byte-true placeholders, not reconstructed source | \ref page_reading_code_staging |

Outside `Code/`: `reverse/functions.csv` is the ledger, one row per retail
function with its source file and status; `reference/shims/` holds shared
headers; `tools/` holds the matching and lookup tools.
\ref page_reading_code explains all three.

## Entry points {#page_mainpage_entry}

The engine starts the way Zero Hour's does, and all of these are matched:

- `WinMain` handles the Windows side (command line, splash screen, single
  instance), then calls `GameMain`. As in Zero Hour, it exits unless the
  launcher is running and answers its handshake.
- `GameMain` calls `CreateGameEngine`, which builds and returns the Windows
  engine object, `Win32GameEngine`. `GameMain` stores it in `TheGameEngine`,
  calls `GameEngine::init` with the command line and hands control to the
  engine's main loop.
- `GameEngine::init` creates and initialises the engine's subsystems, the
  global `TheX` singletons such as `TheGameLogic` and `TheGameClient`.

The main loop and its per-frame step are not yet reconstructed in BFME 2
(Zero Hour names them `GameEngine::execute` and `GameEngine::update`), so the
guide describes their contract only.
\ref page_startup and \ref page_frame_loop follow this path in detail, and
\ref page_architecture shows how the singletons relate.

## BFME 2 and Zero Hour {#page_mainpage_lineage}

Most of the engine's structure is Zero Hour's, and BFME 2 also inherits from
BFME 1. These differences are visible at the level of the whole tree:

- **Logic rate.** BFME 2's frame pacing reads two globals whose shipped
  values are 30 client frames and 5 logic ticks per second
  (`docs/bfme2-network-timing-path.md`). Zero Hour: the logic runs at 30
  frames per second.
- **Graphics.** The W3D library keeps Zero Hour's `DX8Wrapper` name, but the
  matched `DX8Wrapper::Init` loads `D3D9.DLL` at run time, creates the
  Direct3D 9 interface through `Direct3DCreate9` and enumerates the adapters;
  the device is created later.
- **Video.** Zero Hour's device layer has a `VideoDevice` directory for Bink.
  BFME 2's has none, and `Libraries/Source/` carries On2 VP6 decoder code.
  The `Theora` directory holds two VP6 helpers whose text comes from
  libtheora; libtheora itself is not linked.
- **Interface.** BFME 2 adds EA's Apt runtime, which plays the interface's
  Apt movies; Zero Hour has no Apt library. The Zero Hour window manager is
  still present (\ref sub_gui_apt).
- **Scripting.** BFME 2 links Lua 4.0.1 alongside the map script engine; Zero
  Hour has no Lua (\ref sub_scripting).
- **Online.** BFME 2 carries EA's DirtySock code as well as the GameSpy SDK
  (\ref sub_network).
- **Campaign.** The Living World campaign has no Zero Hour counterpart
  (\ref sub_living_world).
- **Start-up.** BFME 2's `WinMain` takes the command line from
  `GetCommandLineW` and converts it to UTF-8 arguments, where Zero Hour's
  parses the narrow `lpCmdLine`.

The subsystem pages list the differences inside each subsystem.

## Maturity {#page_mainpage_state}

Matching proceeds one function at a time, and a function counts as *matched*
only when its source compiles to retail's bytes. Start-up, engine
initialisation and many libraries are largely matched and named; the frame
loop driver is not yet reconstructed; and a large share of the game code still
sits in staging files with placeholder names. Matched code does not yet link
into a complete engine. `README.md` charts the current figures, and
`python3 tools/progress.py` recomputes them. The pages in this guide stick to
code whose identity is settled, so they describe less than the ledger holds.

## Modding notes {#page_mainpage_modding}

- **The repository holds code, not game data.** Of the game itself it keeps
  only the two retail binaries; INI definitions, maps and their scripts, art,
  UI movies, audio and string tables come from a retail install.
  \ref page_modding describes how the engine finds and layers them.
- **A constant in matched code is the shipped value.** The byte check covers
  every instruction, so an integer limit, array size or other constant
  encoded in a matched function's instructions is the one 1.06 uses.
- **The logic side must stay identical between players.** The engine computes
  a CRC of the game logic state (`GameLogic::getCRC`), which includes the logic
  random seed, and a LAN join request carries CRC values from the global
  data, which Zero Hour names the executable and INI CRCs. Zero Hour:
  multiplayer runs in lockstep, every machine simulating the same game from
  the same commands, and these CRCs detect a divergence; a replay re-runs the
  recorded commands. A change to anything on the
  `GameLogic` side therefore risks a mismatch with unmodified players and with
  existing replays and saves. \ref page_architecture explains the split, and
  \ref sub_save_load_crc covers the CRC and save formats.
- **Changes do not belong in this tree.** Matched functions are held to
  retail's bytes by the repository's gates, so a fix or a mod is built on top
  of this source, not inside it. `README.md` lists bug fixes and mods as what
  the finished source makes possible.

## Remastering notes {#page_mainpage_remastering}

- **Most platform code sits in the device layer.**
  `Code/GameEngineDevice/Source/` holds the renderer side (`W3DDevice`),
  keyboard, mouse and local-file code (`Win32Device`) and Miles audio
  (`MilesAudioDevice`). The exceptions are `WinMain` and `Win32GameEngine`,
  whose virtual factory methods create the engine's subsystems; this tree
  keeps both in `GameEngine/Source/Main/` (Zero Hour: `Win32GameEngine` is in
  `GameEngineDevice/Source/Win32Device/Common/`, and its factories are where
  the W3D, Win32 and Miles implementations of the abstract subsystems are
  chosen).
- **The renderer seam is `DX8Wrapper`.** It lives in
  `Libraries/Source/WWVegas/WW3D2/`, loads Direct3D 9 at run time and holds
  the interface the W3D library renders through; \ref sub_w3d_rendering
  describes it.
- **The layouts are 32-bit.** Class layouts reproduce retail's member offsets
  on a 32-bit target and assume 4-byte pointers.
- **The nominal rates are two globals.** The frame-pacing code reads a 30
  frames-per-second render rate and a 5 ticks-per-second logic rate from
  initialised data in `game.dat`; whether anything changes them at run time
  is not yet established. \ref page_frame_loop explains how the two rates
  relate and what is still unreconstructed. Higher frame rates, a memory fix
  and bigger maps are goals on the README's roadmap, not changes in this
  tree.

## Building the guide {#page_mainpage_build}

From the repository root:

    mkdir -p build/doxygen && doxygen docs/doxygen/Doxyfile

Then open `build/doxygen/html/index.html`. It needs Doxygen (tested with
1.9.8) and Python 3, which runs the input filter; nothing is compiled.
Warnings go to `build/doxygen/warnings.log`.

## What the guide covers {#page_mainpage_scope}

The guide is written by hand, and it covers code whose identity and behaviour
are settled. Code that is still being reverse engineered is described by its
contract, or not yet at all, and names that are still placeholders or
unconfirmed leads are left out. Where a statement comes from Zero Hour or
BFME 1 rather than from BFME 2 itself, it says so.

Comments inside the source files are working notes for byte matching. They
are not part of this guide; open a file in the repository to read them.

Contributors start with `docs/doxygen/README.md`, which holds the layout, the
id scheme and the writing rules.
