LZH-Light 1.0 — Sergey Ignatchenko's compressor, as compiled into game.dat
==========================================================================

This record describes BFME 2 (game.dat 1.06, imagebase 0x400000). Until
2026-10-08 it was a copy of Open-BFME-1's record and quoted lotrbfme.exe
addresses and measurements as if they were this image's; they are not, and
the one place the two games differ in this library is the point of the
rewrite (see "compress", below).

The three headers and four .tbl files are that commit's text (the working
copy differs only by CRLF, which the repository normalises). The two .cpp
files are NOT pristine, and differ in two different ways:

    Lz.cpp    comments only: the header block and a note above compress.
              14 diff lines against upstream, every one a comment. No code
              line changed -- and none needed to be, because BFME 2's
              compress is upstream's (below).
    Huff.cpp  the header block, one `present-unmatched` marker, and a CODE
              change: LZHLDecompressor::decompress carries EA's divergence
              from upstream, reconstructed from the retail body at
              0x00692440 and documented in place above the function (the
              per-`_get` negative-return tests dropped, the loop re-tested
              at its bottom, `dstSz`/`srcSz` dereferenced unconditionally).
              That is 40 non-comment diff lines, all inside decompress.

Both files say so in their header blocks, because the licence (below)
requires an altered source version to say so.

One inconsistency is upstream's own and is left as found: Huff.cpp's banner
says "LZH-Light algorithm implementation v 1.01" while Lz.cpp's says "v 1.0".
The repo, this file and the `vendored=lzhl-1.0` tag all say 1.0, after the
release and the directory, not after Huff.cpp's banner. Nothing here depends
on which banner is right — the release is pinned by the commit hash above and
by the 3,104 bytes of table data below, neither of which the banner touches.

Why the initial commit and not the branch tip
---------------------------------------------
`main` carries four post-import commits, each of which is a change to the 1998
code rather than a different vintage of it: an INT32/UINT32 retype for LP64
hosts, two POSIX-socket edits to Lzhl_tcp.cpp, an include-case fix, and a
bounds fix that adds `- LZMATCH` to four `_updateTable` calls inside
LZHLCompressor::compress. Only the initial commit is the release. The two are
distinguishable in the one place the bounds fix lands: compress compiles to
1,741 bytes from the initial commit and 1,747 from `main`. In BFME 2 that
decides it outright — retail's compress IS 1,741 bytes (below).

Why this program and not one of the forks
-----------------------------------------
LZH-Light emits no strings, so there is no banner to read out of the image.
The discriminator is static DATA. Huff.cpp's four `.tbl` files are compiled
into seven initialised arrays, which land in game.dat's `.data` as five
blocks, byte for byte, each at exactly ONE address, in the order the compiler
emits them. Measured against game.dat on 2026-10-08:

    RVA         VA          size
    0x009D9938  0x00DD9938  1,772 B  three statics in one block, in this order:
                                       1,096 B  LZHLEncoderStat::symbolTable0
                                                  Symbol[274], 4 B each  (henc.tbl)
                                         128 B  LZHLDecoderStat::groupTable0
                                                  Group[16], 8 B each    (hdec_g.tbl)
                                         548 B  LZHLDecoderStat::symbolTable0
                                                  HUFFINT[274], 2 B each (hdec_s.tbl)
    0x009DA028  0x00DDA028     64 B  decompress's local _dispTable
    0x009DA068  0x00DDA068     64 B  decompress's local _matchOverTable
    0x009DA0A8  0x00DDA0A8  1,024 B  putMatch's local _dispTable     (hdisp.tbl)
    0x009DA4A8  0x00DDA4A8    180 B  putMatch's local _matchOverTable

Unlike lotrbfme.exe, where the linker left padding between the five blocks,
game.dat packs them 8-aligned: the five run contiguously from 0x009D9938 to
0x009DA55C, where unrelated pointer data begins. The three-way split of the
first block is arithmetic, not assertion: NHUFFSYMBOLS is 274 and
HUFFINT/HUFFUINT are 16-bit (_huff.h:25-27), so 274*4 + 16*8 + 274*2 = 1,772
exactly, and each sub-block reads back at its offset as the matching .tbl:
(7,0x14),(8,0x30),(8,0x31) at +0, (2,0),(3,4) at +1096, 256,257,258 at
+1224. The two 64-byte locals read back as {0,0},{0,1},{1,2},{2,4},{3,8},
{4,16},{5,32},{6,64} and {1,8},{2,10},{3,14},{4,22},{5,38},{6,70},{7,134},
{8,262}; putMatch's _dispTable opens (3,0),(3,1),(4,4),(4,5) as hdisp.tbl.

3,104 bytes of Huffman tables, unique in the image. On top of that, whole
function bodies from these two TUs reproduce retail exactly inside one
contiguous run (the ledger is the count of record, re-derive rather than
quote):

    grep -c 'vendored=lzhl-1.0' reverse/functions.csv     -> 33 rows, 5,150 B
    rows sourced from Huff.cpp + Lz.cpp                    -> 38 rows, 6,928 B
      (the 33 above plus compress 1,741 B, _wrap 10 B, and three
       unwind funclets at 0x007A7BC0/0x007A7BC8/0x007A7BE0 the two
       constructors emit)

and the reasoning carries over because BFME 2's bodies are the same program):

Region
------
RVA 0x00690E10-0x00692ABC. The bounds are witnessed, not assumed: zlib's
`_inflateSyncPoint` (0x00690DE0, 37 B) ends at 0x00690E05 below it and zlib's
`_adler32` starts at 0x00692AC0 above it, both rowed from Compression/ZLib —
the same two neighbours as in lotrbfme.exe. Every row between them is this
library's: 24 from Huff.cpp, 11 from Lz.cpp, `?clearStats@Rva006918B0Owner`
(0x006918B0, Rva006918B0ClearStats.cpp beside them), and two stat-table
resets at 0x00692260 (51 B) and 0x00692360 (67 B) rowed under address names
in Code/GameEngine/Source/Common/SmallGaps/Rva00826740ResetTables.cpp and
Rva00826840ResetTables.cpp as byte-identical BFME 1 donors — their struct
layouts (int[0x89] = 274 HUFFINT, int[0x20] = Group[16]) are this library's
decoder-stat tables, and the address names preserve that no retail name
witnesses them. Compression.dsp says the static library contains nothing else.

The wrappers EA wrote around the library — LZHLCreateCompressor and friends
in CompLibSource/LZHLApi.cpp and NoxCompress.cpp's CompressFile /
DecompressFile / CompressMemory / DecompressMemory and factory thunks, at
0x0068A5F0..0x0068AAA8 and 0x0068EC80..0x0068ED9B — sit outside this run,
below it among zlib's own bodies (zlib's compress2 is at 0x0068AAB0 and its
deflateEnd at 0x0068F1C0); they are EA code and carry no vendored tag.

Where the files sit
-------------------
`Code/Libraries/Source/Compression/LZHCompress/CompLib{Header,Source}` is EA's
own layout for this library, read out of the Zero Hour Compression.dsp file
list. Upstream ships all fourteen files flat (the nine taken here plus Lzhl.cpp,
Lzhl_tcp.cpp, lzhl.h, Lzhl_tcp.h and Test.c); splitting them across the two
directories is why each .cpp carries
`-ICode/Libraries/Source/Compression/LZHCompress/CompLibHeader` on its `// cl:`
line. `/DNDEBUG` is load-bearing (these bodies carry no assert). `/MD` is NOT:
no body claimed here calls the CRT, so it is byte-indistinguishable, and it is
on the line only to match the zlib TUs that share this static library and are
known to need it.

Only Huff.cpp and Lz.cpp are vendored. Lzhl.cpp and Lzhl_tcp.cpp are in EA's
file list but carry no row here, and `build.py`'s `verify_source_claims`
refuses a row-less `Code/**/*.cpp` — so vendoring them would break the gate to
add nothing. Their headers (Lzhl.h, Lzhl_tcp.h) are left out for the same
reason: nothing this tree compiles includes them.

The ledger contract
-------------------
Rows sourced here carry `vendored=lzhl-1.0` and name the upstream's own
identities. There are no `gen-` names among them. `./build.sh <TU>` compiles
the vendored source and byte-compares each row against retail exactly as it
does for code this repo wrote; a row is not evidence of anything until it
passes that.

Two rows in this run carry a tag they should not, inherited from the sweep
that placed them and left as found so the tag's history stays legible:
`?compress@LZHLCompressor@@QAEIPAEPBEI@Z` (0x006911B0) is noted
`stlport-4.5.3` and `?_wrap@LZBuffer@@KAHK@Z` (0x00690F50)
`vendored=stlport-4.5.3`. Neither body touches STLport; both are this
library's, verified from these sources.

The two bodies, and how BFME 2 differs from BFME 1
--------------------------------------------------
1. compress. LZHLCompressor::compress compiles to 1,741 bytes from the
   initial commit (1,747 from `main`), and game.dat's body at 0x006911B0 IS
   1,741 bytes: it matches from the unmodified upstream Lz.cpp, and the row
   is `matched`. This is the one place the two games differ. lotrbfme.exe's
   compress (BFME 1, 0x00825680) is 1,724 bytes — an EA edit to the lazy
   match that Open-BFME-1 reconstructs in its own Lz.cpp — and BFME 2 does
   not carry that edit: its compress is stock LZHL 1.0.

2. decompress. LZHLDecompressor::decompress compiles to 852 bytes from
   upstream; game.dat's body at 0x00692440 is 824 bytes, and Huff.cpp
   carries EA's divergence reconstructed in source (see the comment above
   the function), `matched`, noted `vendored=lzhl-1.0 with EA's divergence`.
   BFME 1's decompress is the same 824-byte shape, so this edit EA made to
   the library once and both games ship it; the compress edit they made
   only once more, for BFME 1.

3. `?_wrap@LZBuffer@@KAHK@Z` and `?_distance@LZBuffer@@KAHH@Z` compile to the
   same ten bytes. One copy is rowed as _wrap at 0x00690F50 (under the
   inherited tag noted above, between the rowed LZBuffer constructor at
   0x00690F20 and its inline destructor at 0x00690F40, where Lz.cpp's COMDAT
   order puts _wrap); nothing in the image distinguishes the two names, so
   _distance is not claimed.

4. `??1HuffStat@@QAE@XZ` is ten bytes of `delete[]` through the
   vector-deleting stub, which retail holds in many places; nothing
   attributes any of them to this TU, so none is claimed and Huff.cpp marks
   the definition `present-unmatched`.

5. The mangled names in the ledger come from THIS source, not from the image.
   game.dat exports none of these symbols and carries no RTTI for them, so
   the C++ type encoding inside a name is the vendored header's, not retail's.
   The `main` branch's `signed int` retype changes
   `?_updateTable@LZHLCompressor@@AAEKKPBEKH@Z` to `...@AAEIIPBEIH@Z` without
   moving one byte of code — proof that the byte claim and the name are
   independent, and that only the byte claim is evidence.
