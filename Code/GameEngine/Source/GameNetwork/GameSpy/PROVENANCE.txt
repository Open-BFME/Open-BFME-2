Open-BFME-2 GameSpy SDK provenance — as compiled into game.dat (BFME 2, 1.06)
==============================================================================

This record describes BFME 2's image (game.dat 1.06, imagebase 0x400000;
addresses below are RVAs unless marked VA). Until 2026-10-08 it was a verbatim
mirror of Open-BFME-1's record (commit 9f4139765ead6d02b8a04bbf167b59f1186a964e)
and quoted lotrbfme.exe addresses and BFME 1 measurements as if they were this
image's. The owner's permission statement is kept word for word below; every
measurement is now this image's. chat/PROVENANCE.txt and peer/PROVENANCE.txt
describe those two directories, which are reconstructions on a different
footing from the rest.

*** PERMISSION HELD BY THE PROJECT OWNER — SEE BELOW BEFORE JUDGING THIS TREE ***

The repository owner states (2026-08-17) that permission for this code has been
obtained. That permission is held by the project out of band; it is NOT derivable
from these files or from the carrier they came through, which is why an agent
reading only the tree will conclude the licence is unestablished and should not
act on that conclusion.

Scope, asked and answered (2026-08-18). The owner was asked directly whether the
permission covers the 2007 GameSpy SDK, specifically the Chat and Peer modules,
and answered that it does. On 2026-08-29 the owner confirmed that the grant
extends to this project, Open-BFME-2, Chat and Peer included (docs/matching.md,
"GameSpy SDK (Chat + Peer included) — permitted"). So extending this lane —
adding TUs, adding rows, vendoring Chat/Peer — is permitted, and does not need
to be re-litigated by each agent that reads the evidence below and reaches the
obvious conclusion from the files alone. That conclusion is correct about the
FILES and wrong about the PROJECT, which is the whole reason this paragraph
exists.

Two limits on the paragraph, so it is not read as more than it is. It records
what the owner stated, not a licence document: no grant text exists in the
sources, and nothing here creates one. And it covers the GameSpy SDK only —
other third-party code in this repository is governed by its own record.

Which SDK this is: a later upstream snapshot than BFME 1's, not "2004 vintage"
------------------------------------------------------------------------------
Dated by string fences and one code shape, measured in game.dat on 2026-10-08.
The per-module changelog.txt files shipped with the 2007/2010 public SDKs
date every feature, so a string retail has or lacks bounds the snapshot:

    has   nick-check table `ABCDEFGHIJKLMNOPQRSTUVWXYZabcdef...[]\`_^{|}-`
          at 0x008E60A0                 -> Chat >= 1.11.19 / Peer >= 2.02.22
                                           ("SDK side nickname checking",
                                           10-15-2004)
    has   `CRYPT des %d %s` 0x008E6334  -> Chat >= 1.11.17 (09-15-2004)
    has   `\cdkeyenc\` 0x008F05A4       -> GP >= 1.09.17 (06-24-2004)
    lacks `\partnerid\`                 -> GP <  1.09.45 (04-12-2006)
    lacks `\sdkrevision\`, `natneg%d.gamespy.com`, any `gsi*` / `GSI_` string
                                        -> pre-2006 core, no NatNeg SDK. The
                                           only "natneg" in the image is the
                                           qr2 key name at 0x008E5B40; NAT
                                           traversal goes through EA DirtySock
                                           ProtoMangle (`/getPeerAddress?...`
                                           at .data 0x009D8740).
    also  `GameSpyHTTP/1.0` 0x008E7828, `HTTP/%d.%d %d%n` 0x008E7864,
          `ATM %s :%s` / `UTM %s :%s` 0x008E6130 / 0x008E613C, `\lc\2`
          0x008F0644, `master.gamespy.com` 0x008E5B03, `peerchat.gamespy.com`
          0x008198D8, `gpcm.gamespy.com` / `gpsp.gamespy.com` at .data
          0x009DDD80 / 0x009DDDC0.

That is exactly lotrbfme.exe's fence set, so both games' snapshots fall inside
Oct 2004 – Mar 2006 and strings alone cannot order them. One code shape does:
ghiParseStatus (ghttp/ghttpProcess.c, 0x006BB4B0, 186 B) tests sscanf's count
(`rcode != 3`) in its own block, before the version/status-code checks. That
shape is in neither the Area 51 carrier nor the 2007/2009 public texts; BFME 1's
ghiParseStatus does not have it; and the ghttp changelog's only ghiParseStatus
entry is 1.07.11, "find the status string after it checks for correct header
information", released 06-03-2005. So game.dat's SDK is a snapshot taken after
BFME 1's (~Oct–Nov 2004) — probably ghttp >= 1.07.11, mid-2005 — and before
Apr 2006. The attribution to 1.07.11 rests on changelog wording alone (the
later public texts re-merged the check), so an EA edit at that one site is not
excluded; the ordering after BFME 1 is what the site establishes.

The ledger tag stays `vendored=gamespy-2004`. Tags are free text to the tools
(they key on the `vendored=` prefix, never the value), so a rename is
mechanically possible; it is not done because the only evidence for "2005" is
the single site above, and a tag renamed on probability reads exactly like
one that was proven. Read the tag as "the Area 51-carried, pre-common/ SDK
generation", and read this section for the date.

Carrier
-------
    github.com/bisc67/Area51, Support/NetworkMgr/GameSpy
    the Area 51 (Inevitable Entertainment / Midway) source release

The only public carrier found with the pre-2006 SDK layout (top-level
nonport.c, no common/), dated by nonport.h's own marker "Added by Saad Nader
on 08-02-2004". Its ghttp predates Jan 2004 (it lacks the per-request proxy
override the changelog dates 01-26-2004), so Area 51 is one licensee's mixed
snapshot, older than either game's. The .c files under this directory are
its text with the deltas below; the SDK headers are not duplicated here —
each TU's `// cl:` line adds `-Ireference/open-bfme-1/.../GameSpy/<module>`,
so the pinned BFME 1 reference tree's headers (the carrier's, with BFME 1's
reconciled ghttpConnection.h) are what compile, resolved layout-agnostically
by tools/build.py.

The "440 byte-exact functions against 51/48 for the 2007 SDK" count that
dated BFME 1's tree was measured against lotrbfme.exe and is not repeated
here. What stands for game.dat is the ledger: every SDK row below is
`matched`, each body compiled from these sources and byte-compared by the
gate.

Why no grant is readable from the tree itself
---------------------------------------------
(This is why the owner's permission above is load-bearing: none of the following
is a grant, so nothing in the files can substitute for it.)

1. The sources grant nothing. Every file here carries a bare
   `Copyright 1999-2001 GameSpy Industries, Inc` block with a postal address,
   phone, fax and a devsupport address line. There is no licence text, no
   reference to a licence, and no LICENSE/COPYING file anywhere in the SDK.

2. The carrier grants nothing either. The Area 51 repository has no LICENSE
   file. Even if it had one, a game studio cannot relicense GameSpy's code:
   Inevitable/Midway were a licensee of this SDK, not its owner.

3. EA's own GPLv3 release does not contain it. In the reference tree,
   `find reference -ipath "*GameSpy*" -name "*.c"` returns ZERO. The party that
   holds the game rights, releasing that game under GPLv3, stripped every line
   of GameSpy C rather than ship it. That is the strongest available signal
   about whether these files could have been distributed under GPLv3, and it
   points the wrong way.

4. The best-informed downstream reads it as proprietary. GameProgressive's
   UniSpySDK — successor to the same team's RetroSpySDK, which had asserted a
   BSD-3-Clause story — dropped that story: its LICENSE states the upstream is
   proprietary Electronic Arts code permitted for NON-COMMERCIAL use only.
   Non-commercial is categorically GPLv3-incompatible. A team revising its own
   licence claim against its own interest is worth more than the claim it
   replaced.

5. The BSD-3-Clause text that circulates for GameSpy is a republisher's. In
   nitrocaster/GameSpy the "IGN Entertainment, Inc." licence file lands in
   726c7851c at 21:22:00Z on 2014-10-15, three minutes BEFORE the sources
   arrive in 1e8bd6fd2 at 21:25:38Z — repository scaffolding, then someone
   else's code. Every apparent corroboration is a copy of that same file.
   (chat/CHAT-SDK-LICENSE.txt is that file, kept as the carrier's text for
   the chat module, not as a grant.)

6. Context: Glu Mobile, which bought GameSpy's technology from IGN in 2012,
   publicly declined to open-source it (May 2014).

Build flags
-----------
`/MD` — retail linked the DLL CRT (msvcr71.dll), so libc calls are `__imp__`
indirect; the static-CRT direct calls do not byte-match. `__cdecl` (i.e. NOT
`/Gz`) — `/Gz` collapses the qr2+GP+ghttp core (measured in BFME 1; the same
bodies here). `/DNDEBUG`. Win32 headers come from `reference/shims/gamespy`
(see its windows.h): the toolchain ships no Platform SDK, and the sweep shim
next door is C++-only.

Chat and Peer: NOT on the same footing as the rest
--------------------------------------------------
The Area 51 carrier ships no chat/ or peer/ directory, so there is no
2004-2005 text to vendor. chat/ and peer/ are RECONSTRUCTIONS: bodies
transcribed from the 2007 SDK (nitrocaster/GameSpy) with local declarations
standing in for the period headers, most of them carried over from
Open-BFME-1's reconstructions and re-placed here (279 of their 586 rows note a
BFME 1 donor). They carry no `vendored=` tag. That the 2007 text reproduces
these bytes says the functions did not change between late 2004 and 2007; it
does not date them, and nothing in the strings separates a Nov 2004 Peer from
a 2005 one. Anchors in game.dat: peer's callbackFuncs[] at 0x008E5DD0 (34
typed rows plus terminator), peerIsAutoMatching 0x006996E0, peerInitialize
0x00699730; chat's gs_prepare_key / gs_crypt / gs_xcode_buf at 0x006A9ED0 /
0x006AA030 / 0x006AA100. Details in chat/PROVENANCE.txt and
peer/PROVENANCE.txt.

BFME2 GHTTP reconciliation, 2026-09-07
------------------------------------
ghttpMain.c, ghttpPost.c and ghttpProcess.c map SDK strdup calls to
msvcr71.dll!_mbsdup, identified by the retail PE import at 0x00BBA5C8;
explicit goastrdup calls remain unchanged. ghttpProcess.c also rejects an
incomplete sscanf result before reading statusStringIndex (the ghiParseStatus
site discussed above). ghttpCommon.c factors proxy parsing into a static C
helper shared by the global and per-request setters. The helper/request-setter
names are descriptive reconstruction names; their original names are absent
from the stripped image. These are source reconciliations, not pristine
upstream functions. Every ledger claim still requires its own complete byte
match, literal check and callee proof.

BFME2 ghttp socket select, 2026-10-02
-------------------------------------
Retail's ghttp callers (ghttpBuffer.c, ghttpProcess.c) reach 0x0060A9F0, the
nonport.c GSISocketSelect body that the carrier's nonport.c itself marks
"Formerly known as ghiSocketSelect"; their matched call sites verify against
it. The carrier's ghttpCommon.c still defines the older ghiSocketSelect, whose
body is not retail's (the link census proves the bytes differ), and being the
only definition it was the copy every ghttp caller linked to. ghttpCommon.c
keeps that upstream text under #if 0 and binds the ghiSocketSelect spelling to
GSISocketSelect with an /alternatename, so the callers link to retail's body.

BFME2 server-browsing reconciliation, 2026-09-07
------------------------------------------------
sb_server.c and sb_serverlist.c use TU-local names matching the retail imports:
_strcmpi for case-insensitive CRT comparisons, and htonl/htons for both directions
of the x86 byte reversal. Separate import slots are accepted only when the PE
explicitly names the same DLL and export. sb_server.c also validates the first
digit after an optional minus sign when reading integer keys. In
sb_serverbrowsing.c, the added-server callback treats pending basic/full queries
as updates already in progress. These ordinary-C changes are inferred from
complete retail bodies, including the actual callback pointers in their callers.

Where this record is weak
-------------------------
- No public SDK snapshot exists between Aug 2004 (Area 51) and Dec 2007
  (nitrocaster); "upstream by 2007" is inferred from changelog dates plus
  presence in the 2007 text, not from a dated intermediate release.
- The 2005 dating rests on one code-shape site matched to changelog wording.
- The four unattributed sites above are undecidable from public material.
