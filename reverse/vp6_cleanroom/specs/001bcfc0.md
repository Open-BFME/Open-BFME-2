name: ReadHeaderBits
rva: 0x001BCFC0
size: 129
ret_site: 0x001BD040
convention: cdecl
args: [esp+4] pointer to the frame header reader (0x0 buffer pointer, 0x4 32-bit window, 0x8 bits available in the window, 0xC byte position of the next unread word), [esp+8] bit count
returns: the bits as an unsigned integer
callees: none
tables: none
fields: header reader 0x4 window, 0x8 bits available, 0xC byte position

Behaviour:
Consumes the next (bit count) bits of a big-endian, most-significant-bit-first stream and returns them right-aligned. The reader keeps a 32-bit window aligned so that its unread bits occupy the top of the window, with a count of how many are available. When the available count covers the request, the bits are taken from the top of the window, the window is shifted up by the count and the available count reduced (0x001BD01C..0x001BD037). When the request exceeds the available bits, the available bits become the high part of the result, the next four buffer bytes at the byte position are loaded big-endian as a fresh window (position advances by 4, 0x001BCFE5..0x001BD012), and the remaining bits of the request are taken from the top of that fresh window, which is then shifted and its available count set to 32 minus the bits taken (0x001BCFF1, 0x001BD022). Window, available count and position are written back. Exact state rules, all consequences of the four variable x86 shifts whose count is taken modulo 32 (0x001BCFEF, 0x001BCFF9, 0x001BD020, 0x001BD035). A state is canonical when every bit of the window below its top (available count) bits is zero, which includes an available count of 0 with a zero window (the canonical empty state). A state is stale when the available count is 0 and the window is not zero. Requests of 1..31 bits: from a canonical state the ordinary contract above holds and the state left is canonical. From a stale state the fresh word is loaded as usual but the result is the ordinary value merged with the stale window shifted up by the request count (truncated to 32 bits), and the state left is canonical (window fresh word shifted up by the count, available count 32 minus the count). Requests of 32 bits: with 1..31 bits available the ordinary contract holds and the state left is canonical with the same available count. With exactly 32 bits available the request returns the window, consumes nothing from the buffer, and leaves the window unchanged with the available count 0, which is stale if that window is non-zero and canonical empty if it is zero. With 0 bits available (canonical empty or stale) the next four bytes are loaded, the position advances by 4, the result is the fresh word merged with the previous window (unshifted), and the state left has that fresh word as window and available count 0, which is canonical empty exactly when the fresh word is zero and stale otherwise. So with 0 bits available a 32-bit request leaves a canonical state only when the next four bytes are all zero. Examples with next bytes 12 34 56 78: from the canonical empty state a request of 32 returns 0x12345678 and leaves window 0x12345678 with 0 available (stale). From window 0x89ABCDEF with 32 available, a request of 32 returns 0x89ABCDEF and leaves the window stale with the position unchanged, after which a request of 32 returns 0x9BBFDFFF instead of 0x12345678 and leaves window 0x12345678 with 0 available (still stale), whereas a request of 1 instead returns 0x13579BDE instead of a single bit and leaves window 0x2468ACF0 with 31 available (canonical). The retail callers (LoadFrameHeader) request only 1, 2, 5, 6 and 16 bits, so the anomalous case never occurs in retail and implementations need only preserve the 1..31 contract.
