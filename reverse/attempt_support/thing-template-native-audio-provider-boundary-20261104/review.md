## Insertion at 0x358E9F

The 148-byte native insertion is in the HotKey address family. It compares AsciiString keys through `0x5598C`, invokes node builder `0x358DA0` twice and rebalances through `0x25490`. `0x358E6A` is erase/clear, not this builder. The InGameUI insertion at `0x2A484A` has the same non-relocation instruction shape but calls its different builder `0x2A42B6`; it is not an interchangeable provider.

The actual HotKey construction/lifetime spine is:

- `0x358DA0`, 34 bytes: allocate 24 bytes, construct value+16 via `0x358CA0`.
- `0x358CA0`, 45 bytes: null-guarded placement copy, calls `0x358B43`.
- `0x358B43`, 34 bytes: copy AsciiString through `0x365F0`; copy pointer at +4 and increment pointee+4 when nonnull.
- `0x358B65`, 57 bytes: release pointer at +4 through `0x7DEEF`, then release the key through `0x36410`.
- `0x7DEEF`, 24 bytes: decrement pointee+4, invoke its virtual deletion path and operator delete at zero.

Thus the four-byte mapped operation is a **counted handle**, not trivial scalar storage, a list or an in-place AudioEventRTS. Existing `TreeHintRef00217D4C` and `ConstructPairHR` express that proven operation; the original pointee/application identity remains opaque.
