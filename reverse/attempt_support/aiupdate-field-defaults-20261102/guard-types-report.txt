AIUpdate guard-field/signature investigation -- 2026-11-02, read-only

Verdict
-------
The +0x68 and +0x6C fields are not transposed. The current canonical storage
declarations are consistent with target uses: +0x68 is a 32-bit team identifier;
+0x6C is the guarded/attacked PolygonTrigger pointer. The neutral virtual
signatures at slots 120/121/122 were misidentified. Keep their neutral names.

Compatible typed ABI contracts for root's subsequent exact trials:
  unsigned int AIUpdateInterface::vslot120() const;
  const PolygonTrigger *AIUpdateInterface::vslot121() const;
  void AIUpdateInterface::vslot122(const PolygonTrigger *);

Unsigned width/team-ID use at slot 120 is supported by an actual matched
consumer. Constness of PolygonTrigger is the existing canonical field and donor
API policy; machine instructions cannot independently establish pointee constness.
The setter's complete body proves a one-word store into that pointer field;
no original setter name or original C++ signature is claimed.

Guard commands:
  privateGuardPosition 0x00264BC2: target-type words are +50/+54; location +58.

  privateGuardObject 0x00264D0E: writes target type 1 to +50/+54 and object ID +64.

    that particular parameter's complete type is not established here.

Constructor 0x0026E9BD zeroes +68 at 0x0026EB1A and +6C at 0x0026EB23.
Zero initialization does not identify either field's semantic type. The private
constructor view's old m_areaToGuard label at +68 is contradicted by consumers;
it is a historical agent spelling, not evidence to transpose the real fields.

Xfer 0x00267EDD keeps the fields distinct:
  0x00268045 takes the address of AI+68, passing it to Xfer vslot +78.
  0x00268051 loads AI+6C, null-checks it, then accesses the pointed object's
    string at +40; the reconstructed matched row serializes its trigger name.
  0x00268096 calls TerrainLogic's trigger-name lookup slot +9C and
  0x0026809C stores the returned pointer into AI+6C.
  Thus +68 is transferred as a scalar word while +6C is resolved as a pointer.

Donor facts, not target-original-name claims
-----------------------------------------
Zero Hour Include/GameLogic/Module/AIUpdate.h:359-364 and696-700 declares
guard location, guarded ObjectID, area pointer and a two-word guard-target stack.
ZH has no intervening team-ID field or team getter. The BFME2-only team word
explains the +4 area displacement and the inserted slot120 getter; slot122 is
another BFME2 callback. Do not transplant the donor's old slot numbering.
BFME2's m_teamToGuard semantic description is supported, but renaming the existing
neutral field is a separate naming-lane decision and is not needed for this repair.

Current users / implications
---------------------------
The canonical m_field068 name occurs only in AIUpdate.h. Current canonical
AIUpdate vslot120/121/122 have no out-of-class definitions under Code/; their
normal declarations and emitted vtable references are the affected ABI names.
Other occurrences of vslot120/121/122 in W3DScriptedModelDrawNukeRender and the
private melee-path view are unrelated or unused slot placeholders, not grounds
for a global identifier replacement.

The private AIUpdate guard/Xfer users above already use correct +68/+6C storage.
Other m_areaToGuard members in AIGuardMachine views at +40/+44 are different
classes and must not be mechanically renamed/retyped with the AIUpdate field.

Retyping these virtual declarations changes decorated symbol spellings even
though every value is one machine word. Root must coordinate provider admissions,
all canonical-header dependents/vtable references and normal full byte/data/EH
gates. No field-order/storage/lifetime change is warranted. No casts are proposed
as the final repair. No source, ledger, header, claims or network changes made.

Native binary slices and full objdump output are saved beside this report in
native-disassembly.txt. No compiler was invoked.
